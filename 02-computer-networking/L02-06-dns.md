## 1. এই lesson-এ যা শিখবেন

- DNS কী সমস্যা সমাধান করে এবং কেন এটি **distributed, hierarchical** database।
- **Stub resolver**, **recursive resolver**, **root/TLD/authoritative server** — একটি query-র পূর্ণ যাত্রা।
- Record type: A, AAAA, CNAME, MX, TXT, NS, SOA।
- **TTL ও caching** — "DNS propagation" আসলে কী।
- Ubuntu-তে name resolution-এর পথ: `/etc/hosts`, `nsswitch`, **systemd-resolved** (`127.0.0.53`)।
- `dig` দিয়ে diagnosis, `+trace`।
- Python দিয়ে নিজের হাতে DNS packet তৈরি ও parse (RFC 1035, compression সহ) এবং আসল resolver-এ query।

## 2. এই ধারণা কোন সমস্যার সমাধান করে

মানুষ নাম মনে রাখে (`app.example.com`), network চলে IP-তে (L02-03)। শুরুর দিকের Internet-এ একটি কেন্দ্রীয় file (`HOSTS.TXT`) সবার কাছে copy হতো — কয়েক হাজার host-এ অচল হয়ে পড়ে। **DNS** নামের জগৎকে ভাগ করে: প্রতিটি domain-এর মালিক নিজের নাম নিজে পরিচালনা করেন, আর বিশ্বজুড়ে cache দিয়ে দ্রুত উত্তর।

DevOps-এ DNS সবচেয়ে প্রচলিত incident-কারণগুলোর একটি ("It's always DNS"):

- Deploy-এর পরে নতুন IP-তে যেতে কিছু user-এর ঘণ্টা লাগে — TTL।
- Server-এ "Temporary failure in name resolution" — resolver configuration।
- Kubernetes-এ service খুঁজে পাওয়া যায় না — cluster DNS (Module 14)।
- Email যায় না — MX record; domain verification — TXT record।
- Load balancer, CDN, cloud service — সবই CNAME/ALIAS-এর উপর।

## 3. সহজ ভাষায় পরিচয়

**DNS** = নাম থেকে তথ্য (মূলত IP) খোঁজার বিশ্বব্যাপী, স্তরভিত্তিক database।

**নামের গঠন** (ডান থেকে বামে স্তর):

```text
app.example.com.
                └─ "." root (সাধারণত লুকানো)
            └─ com     TLD (top-level domain)
    └─ example         domain (আপনার কেনা)
└─ app                 subdomain (আপনি নিজে তৈরি করেন)
```

**ভূমিকা:**

| ভূমিকা | কী করে | উদাহরণ |
|---|---|---|
| **Stub resolver** | Program-এর পক্ষে প্রশ্ন পাঠায় — নিজে খোঁজে না | Linux-এর glibc, systemd-resolved |
| **Recursive resolver** | পুরো খোঁজার কাজ করে, cache রাখে | ISP-র resolver, `1.1.1.1`, `8.8.8.8`, cloud VPC resolver |
| **Root server** | "`.com` কে জানে" বলে দেয় | ১৩টি নামের (বহু copy, anycast) |
| **TLD server** | "`example.com` কে জানে" | `.com`-এর server |
| **Authoritative server** | Domain-এর আসল উত্তর দেয় | Route 53, Cloudflare DNS, আপনার DNS provider |

**প্রধান record type:**

| Type | অর্থ | উদাহরণ |
|---|---|---|
| A / AAAA | নাম → IPv4 / IPv6 | `app 300 IN A 203.0.113.10` |
| CNAME | নাম → আরেকটি নাম (alias) | `www → app.example.com` |
| MX | Email কোন server-এ (priority সহ) | `10 mail.example.com` |
| TXT | মুক্ত text — verification, SPF, DKIM | `"v=spf1 include:... -all"` |
| NS | এই zone-এর authoritative server কারা | |
| SOA | Zone-এর প্রশাসনিক তথ্য (serial, negative TTL) | |

**TTL** = record কতক্ষণ cache-এ রাখা যাবে (সেকেন্ডে)।

## 4. বাস্তব জীবনের উদাহরণ (analogy)

### ফোনের contact list ও তথ্যকেন্দ্র

- **নিজের contact list** (`/etc/hosts` ও local cache) — আগে এখানে দেখেন।
- না পেলে **তথ্যকেন্দ্রে** ফোন (recursive resolver) — "রহিম সাহেবের নম্বর দিন"।
- তথ্যকেন্দ্র জানে না, তাই খোঁজে: জাতীয় ডিরেক্টরি (root) → "ঢাকা অফিসে জিজ্ঞেস করুন" (TLD) → ঢাকা অফিস → "রহিম সাহেবের কোম্পানির রিসেপশনে" (authoritative) → নম্বর পায়।
- তথ্যকেন্দ্র নম্বরটি **খাতায় লিখে রাখে** (cache) — "এক ঘণ্টা বৈধ" (TTL)। পরের জন জিজ্ঞেস করলে সরাসরি খাতা থেকে।

### Analogy কোথায় মেলে না

- রহিম সাহেব নম্বর বদলালে তথ্যকেন্দ্র হয়তো ফোন করে জানতে পারে। DNS-এ **কেউ cache-কে জানায় না** — পুরোনো উত্তর **TTL শেষ না হওয়া পর্যন্ত** দেওয়া হতে থাকে। "Propagation" আসলে বিশ্বের হাজারো cache-এর TTL একে একে শেষ হওয়া (Section 5)।
- তথ্যকেন্দ্রের উত্তর সাধারণত বিশ্বাসযোগ্য। Plain DNS (UDP ৫৩) encrypted বা authenticated নয় — পথে কেউ মিথ্যা উত্তর দিতে পারে (cache poisoning)। DNSSEC (সই করা উত্তর) ও DoT/DoH (encrypted transport) এর প্রতিকার, তবে সর্বত্র নয়।
- "নম্বর নেই" বলাও cache হয় — **negative caching** (NXDOMAIN-এর TTL SOA থেকে)। নতুন record তৈরির আগে কেউ জিজ্ঞেস করে থাকলে কিছুক্ষণ "নেই" উত্তর পেতে থাকবে।

## 5. Real-world engineering scenario — Migration ও ২৪ ঘণ্টার TTL

**পরিস্থিতি:** Website নতুন server-এ সরানো হচ্ছে (পুরোনো IP `198.51.100.5` → নতুন `203.0.113.10`)। শনিবার রাতে A record বদলানো হলো, পুরোনো server বন্ধ। রবিবার সকালে অর্ধেক user বলছেন site খোলে না।

**কারণ:** Record-এর TTL ছিল **৮৬৪০০** (২৪ ঘণ্টা)। যে resolver-গুলো শনিবার বিকেলে উত্তর cache করেছিল, তারা রবিবার বিকেল পর্যন্ত পুরোনো IP দেবে — যেখানে এখন কিছু নেই।

**Diagnosis:**

```bash
dig +short app.example.com @1.1.1.1          # একটি public resolver কী দেখছে
dig +short app.example.com @8.8.8.8          # আরেকটি — ভিন্ন হতে পারে
dig app.example.com @ns1.example-dns.com     # authoritative-এর উত্তর (নতুন IP) — ground truth
dig app.example.com | grep -A1 "ANSWER SECTION"   # TTL কলাম: এই resolver-এ আর কতক্ষণ cache
```

**সঠিক পদ্ধতি (পরের বার):**

1. Migration-এর **অন্তত পুরোনো TTL-এর সমান সময় আগে** TTL কমিয়ে ৩০০ (৫ মিনিট) করুন।
2. পুরোনো TTL পার হওয়ার অপেক্ষা।
3. Record বদলান — এখন সবাই ৫ মিনিটে নতুন IP পাবে।
4. **পুরোনো server কিছুক্ষণ চালু রাখুন** (অথবা নতুন server-এ proxy করুন)।
5. সব স্থির হলে TTL আবার বাড়ান।

**শিক্ষা:** DNS পরিবর্তন তাৎক্ষণিক নয় — TTL হলো আপনার rollback ও migration-এর গতির সীমা। Low TTL-এর খরচ: resolver-এ বেশি query (সামান্য latency ও কিছু DNS provider-এ বিল)।

## 7. গুরুত্বপূর্ণ terminology

|---|---|

| Negative caching | "নেই" (NXDOMAIN) উত্তরও cache |

| Split-horizon DNS | ভেতর ও বাইরের জন্য আলাদা উত্তর |

## 8. ভেতরে কীভাবে কাজ করে

### 8.1 DNS message-এর গঠন (RFC 1035)

```text
 Header (12 byte): ID | flags (QR, opcode, AA, TC, RD, RA, rcode) | QDCOUNT | ANCOUNT | NSCOUNT | ARCOUNT
 Question:         QNAME (label-ভিত্তিক) | QTYPE | QCLASS
 Answer/Authority/Additional: NAME | TYPE | CLASS | TTL | RDLENGTH | RDATA
```

**Name encoding:** `www.example.com` → `03 w w w 07 e x a m p l e 03 c o m 00` (প্রতিটি label-এর আগে দৈর্ঘ্য)।

**Compression:** উত্তরে একই নাম বারবার এড়াতে — byte-এর প্রথম দুই bit `11` হলে বাকি ১৪ bit = message-এর ভেতরে আরেকটি offset ("নামের বাকিটা ওখানে")। এই lesson-এর parser এটি অনুসরণ করে, এবং infinite loop (নিজের দিকে pointer) প্রত্যাখ্যান করে — ক্ষতিকর packet থেকে সুরক্ষা।

**Flags:** `RD` (recursion desired — stub চায়), `RA` (recursion available — resolver পারে), `AA` (authoritative answer), `TC` (truncated — UDP-তে আঁটেনি, TCP-তে আবার জিজ্ঞাসা করো)।

**Transport:** সাধারণত UDP ৫৩ (L02-05); বড় উত্তর বা zone transfer-এ TCP ৫৩। তাই firewall-এ DNS-এর জন্য **TCP ৫৩-ও** খোলা দরকার হতে পারে।

### 8.2 Ubuntu-তে resolution-এর পথ

- `/etc/nsswitch.conf`-এর `hosts:` লাইন ক্রম ঠিক করে (সাধারণত `files` আগে = `/etc/hosts`)।
- `/etc/resolv.conf` → সাধারণত symlink, `nameserver 127.0.0.53` — **systemd-resolved**-এর local stub ও cache।
- আসল upstream server দেখতে: `resolvectl status`।
- **`dig`/`nslookup` nsswitch ও `/etc/hosts` উপেক্ষা করে** সরাসরি DNS-এ যায়; application যায় `getaddrinfo` দিয়ে (nsswitch মেনে)। তাই "`dig` ঠিক উত্তর দিচ্ছে কিন্তু app ভুল IP-তে যাচ্ছে" — প্রায়ই `/etc/hosts`-এ পুরোনো entry। Application-এর দৃষ্টিতে দেখতে: `getent hosts NAME`।

> **Fedora-তে:** Fedora 33 থেকে systemd-resolved default — একই `resolvectl` ও `127.0.0.53`।

### 8.3 Cloud ও container-এ DNS

- AWS VPC-তে resolver VPC CIDR-এর base + ২ ঠিকানায় (L02-03-এর সংরক্ষিত ঠিকানা) এবং `169.254.169.253`।
- Docker container সাধারণত host-এর resolver configuration বা Docker-এর embedded DNS (`127.0.0.11`) পায় (Module 10)।
- Kubernetes-এ CoreDNS + `ndots` setting — অতিরিক্ত query ও latency-র পরিচিত উৎস (Module 14)।

## 9. Practical demonstration

### 9.1 Query নিজের হাতে তৈরি

File: [`code/L02-06/dns_wire.py`](code/L02-06/dns_wire.py)

```bash
cd ~/devops-ai-engineering/02-computer-networking/code/L02-06
python3 dns_wire.py build example.com A
```

**আসল output:**

```text
123401000001000000000000076578616d706c6503636f6d0000010001
```

| Byte (hex) | অর্থ |
|---|---|
| `1234` | ID |
| `0100` | Flags: RD = ১ |
| `0001 0000 0000 0000` | ১টি question, ০ answer/authority/additional |
| `07 6578616d706c65 03 636f6d 00` | `example` (৭ byte), `com` (৩ byte), শেষ |
| `0001` | QTYPE = A |
| `0001` | QCLASS = IN |

মোট মাত্র ২৯ byte — DNS কেন UDP-তে দ্রুত।

### 9.2 আসল resolver-এ query

```bash
python3 dns_wire.py query example.com A                     # system resolver (Ubuntu: 127.0.0.53)
python3 dns_wire.py query example.com A --server 1.1.1.1
python3 dns_wire.py query nonexistent-zz9.example A --server 1.1.1.1; echo "exit=$?"
python3 dns_wire.py query gmail.com MX --server 1.1.1.1
```

**এই repository-তে ২০২৬-১০-২৬-এ আসলে চালিয়ে পাওয়া output** (IP ও TTL সময়ের সাথে বদলায় — আপনার ফল ভিন্ন হবে):

```text
server 1.1.1.1  status NOERROR  authoritative False  recursion-available True  truncated False
  example.com                         37  A     104.20.23.154
  example.com                         37  A     172.66.147.243
```

```text
server 1.1.1.1  status NXDOMAIN  authoritative False  recursion-available True  truncated False
exit=1
```

```text
server 1.1.1.1  status NOERROR  authoritative False  recursion-available True  truncated False
  gmail.com                         1981  MX    40 alt4.gmail-smtp-in.l.google.com
  gmail.com                         1981  MX    30 alt3.gmail-smtp-in.l.google.com
  gmail.com                         1981  MX    10 alt1.gmail-smtp-in.l.google.com
  gmail.com                         1981  MX    5 gmail-smtp-in.l.google.com
  gmail.com                         1981  MX    20 alt2.gmail-smtp-in.l.google.com
```

**পর্যবেক্ষণ:**

- `authoritative False` — ১.১.১.১ recursive resolver, authoritative নয়।
- `example.com`-এর দুটি A record ও TTL **৩৭** — অর্থাৎ এই resolver-এর cache-এ উত্তরটির আর ৩৭ সেকেন্ড বাকি ছিল (মূল TTL এর বেশি)। আবার চালালে সংখ্যা কমতে দেখবেন — cache নিজের চোখে।
- MX-এ priority: কম সংখ্যা = বেশি অগ্রাধিকার (৫ প্রথমে চেষ্টা)।
- NXDOMAIN-এ exit ১ — script-এ যাচাইযোগ্য।

### 9.3 Native tool (Ubuntu VM)

```bash
dig example.com                       # পূর্ণ উত্তর: header, flags, TTL, কোন server, সময়
dig +short example.com AAAA
dig example.com @1.1.1.1 +norecurse   # resolver-এর cache-এ না থাকলে উত্তর নেই
dig +trace example.com                # root থেকে authoritative পর্যন্ত নিজে হেঁটে
dig -x 1.1.1.1                        # reverse lookup (PTR)
resolvectl status | head -20          # কোন upstream server
resolvectl query example.com          # systemd-resolved-এর দৃষ্টিতে (cache সহ)
getent hosts example.com              # application যা দেখে (nsswitch, /etc/hosts সহ)
```

`dig` না থাকলে: `sudo apt install dnsutils` (Fedora: `bind-utils`)।

**`/etc/hosts`-এর প্রভাব দেখুন (⚠️ পরে মুছুন):**

```bash
echo "203.0.113.99 example.com" | sudo tee -a /etc/hosts
getent hosts example.com              # 203.0.113.99 — application এটাই পাবে
dig +short example.com                # আসল IP — dig /etc/hosts দেখে না
sudo sed -i '/203.0.113.99 example.com/d' /etc/hosts
```

## 10. Code-এর ব্যাখ্যা

| অংশ | কী করে | কেন |
|---|---|---|
| `encode_name` + `encode("idna")` | Label-length encoding; আন্তর্জাতিক নাম | RFC 1035 ও IDN |
| `read_name` + `0xC0` | Compression pointer অনুসরণ | উত্তরের আকার কমানোর জন্য প্রায় সব server ব্যবহার করে |
| `depth > 10` | Loop প্রতিরোধ | ক্ষতিকর packet-এ অসীম recursion নয় |
| `struct.unpack("!HHIH")` | type, class, TTL, rdlength | Network byte order |
| ID মিলানো | `resp.qid != query id` → error | Spoofed/পুরোনো উত্তর প্রত্যাখ্যান (আসল resolver আরো কিছু যাচাই করে, যেমন random source port) |
| UDP timeout | `settimeout` | L02-05: UDP-তে উত্তরের নিশ্চয়তা নেই |
| `except OSError` | timeout, unreachable | Network না থাকলে স্পষ্ট error |

**সীমাবদ্ধতা:** TCP fallback (TC flag), EDNS, DNSSEC যাচাই, retry নেই — production-এ `dig`, `resolvectl` বা `dnspython`।

## 13. Security, performance ও cost বিবেচনা

- **Security:** DNS plain text — পথে দেখা ও বদলানো সম্ভব; DNSSEC ও DoT/DoH। Open resolver (যে কাউকে উত্তর দেয়) DDoS amplification-এ ব্যবহৃত — নিজের resolver শুধু নিজের network-এ। Dangling CNAME (মুছে ফেলা cloud resource-এর দিকে CNAME) = **subdomain takeover** ঝুঁকি — resource মুছলে DNS record-ও মুছুন (Module 19)। DNS দিয়ে data exfiltration — security monitoring-এ DNS query log গুরুত্বপূর্ণ।
- **Performance:** প্রতিটি নতুন নামে lookup latency; local cache (systemd-resolved) ও যুক্তিসঙ্গত TTL; Kubernetes `ndots`।
- **Cost:** Managed DNS-এ query-প্রতি বিল (খুব কম TTL = বেশি query); DNS ব্যর্থতার ব্যবসায়িক খরচ বিশাল — দুটি DNS provider বা নির্ভরযোগ্য managed service।

## 18. সংক্ষিপ্ত সারাংশ

- DNS = স্তরভিত্তিক, distributed নাম-database: root → TLD → authoritative; recursive resolver খোঁজে ও cache করে।
- Record: A/AAAA, CNAME, MX, TXT, NS, SOA।
- **TTL** = পরিবর্তনের গতি ও rollback-এর সীমা; negative caching।
- Ubuntu: nsswitch → `/etc/hosts` → systemd-resolved (`127.0.0.53`); `dig` hosts উপেক্ষা করে, `getent` করে না।
- Plain DNS অরক্ষিত — DNSSEC, DoT/DoH; dangling CNAME সাবধান।
